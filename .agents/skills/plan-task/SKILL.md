# 讨论沉淀为方案与任务清单（plan-task）

日常讨论（功能设计、交互方案、配置扩展等）→ 沉淀为 z.plan.md 附录方案 + x.progress.md 任务清单。只写文档，不修改业务代码。

> 本文件为项目自建 skill 权威源（`.opencode/skills/` 同名旧版为字母系列取号规则的历史副本，已废弃，以本文件三线轨道为准）。

## 编号规则（MM 2026-11-05 定稿；三线轨道）

- **方案（z.plan.md）**：`## 附录 PL{NNN}：{标题}（YYYY-MM-DD 立项）`，追加在文末附录区（A 审计附录之后亦按文档实际顺序排布；写入前核对 `## 附录 PL\d{3}` 无同名占用）
- **任务组（x.progress.md）**：`### PL{NNN}: {标题} [z.plan#附录 PL{NNN}]`，写入 `## 未完成` 区末尾；子任务 `- [ ] PL{NNN}.{序号} {标题} —— {做法}；验证：{检验方式}`
- **同号绑定**：方案 PL{NNN} 与任务组 PL{NNN} 同号；取号 = 搜索 x.progress.md / z.plan.md 中 `PL\d{3}` 的最大值 +1（无历史时 PL001）
- **轨道区分**：功能里程碑用 PL；审计修复走 FIX（audit-report）；用户日常小修小改走 PATCH（直接立项，不源自讨论沉淀流程时无需 z.plan 附录，条目入 x.progress.md `### PATCH{NNN}` 组）
- 待评估/暂不定案的内容 → `y.problem.md`（编号延续其 P 序列，引用格式 `[problems#N]`），**不占 PL 编号**

## 执行流程

### Step 1：询问环节（必做）

向用户确认以下规则（展示默认值，用户可改）：

1. **内容去向**：已定案/有决策 → z.plan.md 附录 PL{NNN}；仅待评估 → y.problem.md
2. **PL 编号**：默认当前最大值 +1
3. **粒度**：单条清单 vs 拆分为子任务（默认拆到文件/函数级——AGENTS「任务清单纪律」硬性要求）
4. **版本映射**：是否在本期推进 base.json 的 Z 位（PL 收口时推进；默认每个 PL 一个内容版本）

### Step 2：写入 z.plan.md 附录

- 追加 `## 附录 PL{NNN}：{标题}（YYYY-MM-DD 立项）`
- 内容结构（对齐 CapsulePulse 附录格式）：
  - 状态行：`> 状态：📌 待实施（任务组见 x.progress.md「PL{NNN}」）`（依赖关系一并注明）
  - **定案口径**：方向决策逐条列出（每条一句定案 + 理由/依据）
  - **明确不做**：边界外内容显式排除（防 scope 蔓延）
  - **实施与证据**：指向 x.progress.md 对应任务组（实现细节以代码与 git 历史为准，附录不复制）
- **必须含决策结论**；待定内容写 y.problem.md，不进 z.plan

### Step 3：写入 x.progress.md

- 在 `## 未完成` 区末尾追加 `### PL{NNN}: {标题} [z.plan#附录 PL{NNN}]`
- 组头部 `> 目标：…`（一句话）+ 依赖说明
- 每条格式：`- [ ] PL{NNN}.{序号} {标题} —— {做法}；验证：{检验方式}`
- **做法拆到文件/函数级**（改哪个文件哪个方法、新增什么、怎么改）；验证方式可执行可断言（探针名/断言值/截图读图点/冒烟 import）；收口条目固定含：版本推进 + README 徽章 + a1 断言同步 + 全量回归 + 截图终审 + 草拟 commit

### Step 4：汇报

- 归档位置与编号（附录 PL{NNN} + 任务组 PL{NNN}）
- 询问用户：是否立即执行（触发 progress-task 流程）

## 硬性约束

- 只写 z.plan.md / x.progress.md / y.problem.md，不修改业务代码
- 编号必须先询问确认（用户是编号的最终决定者）
- 编号递增按"最大值+1"，不允许跳号或重复
- 方案必须含决策结论与"明确不做"；待定内容不进 z.plan（进 y.problem.md）
- 条目做法必须文件/函数级（AGENTS 任务清单纪律；因做法缩略被退回重写为先例）
- 不擅自执行 git 写操作（提交由用户执行）
