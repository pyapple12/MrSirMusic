# 项目全量审计（audit-project）

> 规则版本：MM 2026-11-05（对齐 CapsulePulse 现代范本；本文件为项目自建 skill 权威源，`.opencode/skills/` 同名旧版为历史副本不再维护）

对 MrSirMusic 进行全量、全部、全文审计。**只读，绝不修改任何代码**；输出报告，修复由用户另行指示。

## 审计规则来源

执行前先读取：

- `AGENTS.md`：工程原则（KISS/DRY/SOLID、架构与工程决策）、错误策略（**fail-soft 主线 + 容错登记制**——白名单唯一权威源在 AGENTS.md 错误策略节，未登记的静默兜底一律报 P 级）、函数注释规则（函数下 `#` 注释 / 文件尾 `# =====` 说明区，禁止 docstring 当注释）、代码约定（命名/类型注解/import 三段顺序/pathlib 强制/版本双轨）、验证与门禁
- `z.plan.md`：核心机制设计（第六节）与架构约束（第七节），对照实现偏差；"观察项豁免定案清单"（已定案项不再重复报告；执行以本 SKILL.md 为权威，冲突时从本文件）
- `config/static/*.json`：参数外置契约（审计"该进配置未进"的依据）

## 执行流程

### Step 1：读取规则

先读 AGENTS.md（含工程原则、错误策略与容错登记制），明确规范基线

### Step 2：范围界定

- Python 侧：`main.py` + `config/` + `modules/` + `ui/` + `utils/` 下全部 `.py`
- 静态配置：`config/static/` 全部 json（`base.json` 版本字段按 AGENTS「版本双轨」核对：三段式；README 徽章 == base.json version 且链接指向 Releases 页）
- 用户配置：`config/user_config.json` 运行时生成不审
- 资源文件：`data/`（占位图/贴图/音效）与探针产物为二进制不逐字节审，但核对"是否被引用、路径是否经 `utils/paths.py` 解析"
- **不审计** `.temp/`、`.agents/`（skills 自身）、`.opencode/`、`.reference/`（外部参考仓）、`.venv/`、`music/`（用户运行时数据）
- **范围外声明**：无（单仓自含）；后续新增独立仓在此登记豁免
- 文档类 md（w/x/y/z 四文件）作辅助阅读不计问题条目，但核对文档一致性（版本三方一致：base.json / README 徽章 / 最近 commit 标题）

### Step 3：回归复核

读取上轮审计报告（z.plan.md 附录 `A{NNN}`，历史报告为 A001–A005）的 P 级修复清单 → 逐项查代码确认修复是否仍在（grep 关键行）与是否引入新问题；**对多处修改型修复项，有 git 历史时用 `git show <上轮提交>` 对比完整性防漏改**（grep 在位 ≠ 修改完整）→ 报告第零节输出"上轮修复复核表"（首轮无上轮则省略零节，写"无上轮"）

### Step 4：全量通读

逐文件全文阅读（不只读注释）

### Step 5：并行加速（可选）

**环境有子任务/子代理能力时**，按依赖分层三路并行派发**只读探索代理**——modules 核心组（items/rules/generator/library/tagging/cover）、playback 组（engine/queue/events/bus/progress/decoders）、UI 组（ui/ 全部 + themes + bridge）；**环境没有该能力时改为串行逐组执行**（结论等价，只是慢些），不得因无并行能力而跳过本步或缩减范围。三路题面模板见文末。

### Step 6：汇总输出与自查

1. 汇总三路结果：按类别归组 → 跨组同根因合并去重 → 严重度统一排序 → 生成四节报告（格式见"报告格式"）
2. 生成后自查：编号连续、文件:行号真实存在、无错别字/异常字符（通读一遍）
3. 报告编号：审计环节用"第 N 轮"，A 编号由归档环节（audit-report 询问用户后）分配

## 报告格式（四节结构）

```

| 上轮条目 | 现状（✅仍在 / ⚠️回退 / ❌引入回归） | 证据（文件:行号） |
## 一、P0-P3 修复清单（按严重度）
| 文件:行号 | 类型 | 描述 | 建议 | 性质[新增|遗留] | 影响面 |
## 二、参考级观察项（记录不修；含回落理由，用户可复核提升）
| 文件:行号 | 描述 | 回落理由（豁免条件命中哪条） |
## 三、亮点（合规良好处，可省略）
```

- **影响面取值**：播放引擎 / 音频解码 / 物品生成 / 封面服务 / 物品库 / UI 交互 / 显示层 / 配置体系 / 日志 / 跨模块 / 文档

### 参考级观察项（豁免降级）范围

以下类型**记录但不进入 P0-P3 修复清单**（仍含 文件:行号）：

- UI 几何/外观细节参数（绘制色、间距、字号、动画时长——视觉常量豁免先例）
- 有注释/文档依据的算法参数（合成音效参数、惯性系数等）
- 单次使用且无调参场景的模块常量
- 重依赖延迟导入（PySide6/QtMultimedia 按既有惯例延迟引入——AGENTS 例外条款）
- 无可达触发路径的防御性理论缺口（回落时标注"纯理论，需验证"）

### 豁免判定标准（以下条件之一命中即可回落观察项，否则一律报 P 级）

1. 无外部调参场景（参数只在单一算法内部，改动无实际意义）
2. 有注释/文档说明其依据
3. 不是配置键承诺（"该进配置但没进"一律 P2，**不可豁免**）
4. 无可达触发路径（纯理论缺口；回落理由中标注"需验证"）

## 硬性约束

- **绝不修改任何代码**（审计=只读；修复需用户明确指示后另开任务）
- 问题条目必须含 文件:行号，便于定位；无法定位的合并描述并标注
- 严重度判定：**高 = 必须有确定性复现**（代码可证明崩溃/错值）；"可能/理论"一律 ≤ 中
- 同一根因多处出现 → 合并一条（列全部位置），不拆分刷条目
- **豁免清单必填**（无豁免也写"无"），杜绝偷懒默认
- 报告如实，不夸大不遗漏；不确定的条目标注"需验证"
- 探针体系（.temp/probe_a1–a14）为行为事实源：审计结论与探针断言冲突时以实跑为准
- 审计完成后询问用户：①是否按优先级开始修复（触发 progress-task）②是否归档审计报告（触发 audit-report：询问编号 → 写入 z.plan.md 附录 `A{NNN}` + x.progress.md 任务组 `FIX{NNN}`）
